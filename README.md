# 📡 Учебник MikroTik — Android + Windows + интерактивный стенд

Автономное приложение-учебник по настройке роутеров **MikroTik (RouterOS)** с подробными
инструкциями, скриншотами WinBox и готовыми командами CLI — плюс **интерактивный стенд**,
который моделирует конфигурацию под вашу задачу и выдаёт пошаговую инструкцию для
реального роутера.

## Возможности

| Раздел | Содержание |
|---|---|
| 🔌 Подключение провайдера | PPPoE (логин/пароль), DHCP, статический IP, USB 3G/LTE-модем |
| 📶 LAN и Wi-Fi | Подсети, пулы адресов, DHCP, **рабочая и гостевая** Wi-Fi-сети с изоляцией |
| 🛡️ Firewall и NAT | Правила защиты (input/forward), masquerade, порт-форвардинг внутренних ресурсов |
| 🔁 Резервный канал | Маршруты distance, проверка статического шлюза или внешнего узла; проверка отказа на устройстве |
| 🧭 Маршрутизация | Статический маршрут в LAN, VLAN; пояснения по таблицам RouterOS v7, DNS, NTP и IP Cloud |
| 🔐 VPN | **Все типы MikroTik**: WireGuard, IPsec IKEv2, L2TP/IPsec, site-to-site, PPTP, L2TP, SSTP, OVPN |
| 🧪 Лаборатория | Карта устройств, соединения и учебная модель трафика |
| 🛠 Стенд | Ввод задачи → план адресации → проверка модели → конфигурация RouterOS → инструкция реализации |
| ⌨️ Шпаргалка | Частые команды CLI и приёмы WinBox |

**Виртуальная RouterOS на Windows:** в настройках MikroTik есть кнопка «Открыть
RouterOS». Установщик включает QEMU и около 840 МБ соответствующих исходников;
первый запуск скачивает официальный CHR 7.23.8 после ознакомления с лицензией и
согласия. После успешной проверки модели в Windows доступен прямой запуск CHR из результатов; открывается WebFig, не WinBox. Автоматические снимки конкретной схемы пока не создаются. В учебнике кнопка «Проверить на стенде» предлагает подготовленные сценарии для первичной настройки, IP, Interfaces, Bridge, Routing и System; конфликтующие функции не переносятся, неподдерживаемые явно отмечены. В разделе IP можно выбрать учебный dstnat для сервера; проверяются правила, а не доступность сервера снаружи. Для остальных разделов сценарии ещё не готовы. В изолированной CHR поддержан один статический или DHCP WAN и базовые LAN/VLAN, DHCP LAN, DNS, NAT, firewall и настройки NTP с часовым поясом. DHCP WAN получает аренду от QEMU 10.0.2.0/24, а не от физического провайдера; это не подтверждение маршрута или интернета. LAN и гостевая сеть не должны пересекаться с этой сетью. В изолированной CHR проверяется конфигурация NTP, но синхронизация невозможна. В режиме двух виртуальных WAN NTP также доступен после отдельного согласия на сетевой доступ; приложение проверяет конфигурацию, а не синхронизацию выбранного сервера. Однопровайдерный режим изолирован. Для двух виртуальных статических
WAN предусмотрен ограниченный режим доступа к интернету через Windows: только
после предупреждения и отдельного согласия на каждый запуск, поскольку CHR
может обращаться к компьютеру и устройствам LAN. Два WAN используют одно
соединение Windows, а не двух независимых провайдеров; реальные адреса не
подменяются. Требуются заданные виртуальные адреса и DNS из учебника, другие
конфигурации блокируются. Кнопка «Пример CHR: два WAN» создаёт эту учебную
схему после подтверждения замены текущей и сама не включает сеть. ПК и провайдеры схемы не эмулируются; после
применения настройки сверяются в CHR, при закрытии временный диск удаляется.
Android, Wi-Fi/LTE, VPN и резервирование двух роутеров не поддерживаются этим
режимом. Системный диалог и весь запуск установленного приложения пока не
прошли сквозной автоматический тест; снимки всех действий ещё не готовы.

**Физический MikroTik:** в Windows-карточке роутера добавлен экспериментальный поиск соседей по MAC через MNDP после отдельного подтверждения. Можно выбрать найденную строку и вручную скопировать MAC в отдельный WinBox; выбранные данные не сохраняются. Найденные имена и MAC не аутентифицированы: проверяйте MAC на корпусе. Это только поиск; подключение по MAC, сброс и отправка схемы на физический роутер пока **не реализованы**. В изолированном Linux CI официальный WinBox вошёл по MAC в виртуальную CHR; экспериментальный сторонний клиент после CI-only исправления прочитал версию, но не включён в приложение. На физическом устройстве и в Windows-сети поиск и MAC-сеанс ещё не проверены. В отдельном Windows CI исследовательский клиент считал тестовые версию, имя и MAC виртуальной CHR через localhost-мост; найдены недостаточные проверки одного пути приёма. CI-исправления не включены в приложение и не доказывают безопасность. Кнопка «Сохранить и оценить схему» показывает черновую сводку без соединения. По желанию можно вручную ввести имена Ethernet-портов и сравнить их с именами в схеме; список не сохраняется. Это не проверка устройства, не окончательный план изменений и не оценка совместимости. Для ручного входа можно отдельно открыть выбранный пользователем WinBox, не передавая ему пароль или команды; лаборатория не контролирует эту сессию. В дополнительном CI экспериментальный клиент отправил фиксированную учебную конфигурацию одноразовой CHR через искусственный локальный мост и результат был отдельно сверен; это **не функция приложения** и не испытание физического подключения. Подробности — `docs/physical-router-plan.md`.

**Лаборатория:** один MikroTik с одним или двумя провайдерами и LAN /24 без петель;
либо два MikroTik с общим коммутатором LAN и отдельным провайдером на каждом, либо две независимые сети с отдельными роутерами и провайдерами. У каждого
устройства есть ON/OFF; после запуска синие и зелёные полоски показывают условный путь
туда и обратно. При изменении состояния путь пересчитывается. В настройках основного
MikroTik включаются резервный интернет и учебное переключение на второй роутер.

ПК и серверы в лаборатории поддерживают от одной до четырёх сетевых карт. Каждая карта
назначается отдельной линии и имеет собственные сегмент и адресацию; неподключённые карты
не участвуют в расчёте. Устройство не моделируется как мост. Публикация порта привязана к
первой карте, а выбор маршрута ОС, метрики и действительные соединения не моделируются. В независимых сетях адаптеры одного сервера можно подключить к разным роутерам: каждая сеть рассчитывается отдельно, переключения между ними нет. ВМ и виртуальные коммутаторы гипервизора необходимо настроить и проверить самостоятельно.

Для **одного** MikroTik в настройках доступны основной сегмент LAN, гостевой VLAN с
изолированным access-портом, отдельным DHCP и правилами firewall, рабочий и гостевой Wi‑Fi.
Модель поддерживает одну гостевую подсеть /24 и неуправляемые коммутаторы: на одной ветке
моста нельзя смешивать основную и гостевую сеть. VLAN/Wi‑Fi в схеме резервирования с общим LAN двух роутеров пока не
поддерживаются; в независимых сетях каждый роутер рассчитывается отдельно. Радио не эмулируется; команды Wi‑Fi рассчитаны на RouterOS 7.13+ с пакетом
`wifi`, поддерживающим AP/виртуальный SSID. Старый `wireless`, `wifiwave2`, trunk-порты и
изоляция проводных клиентов внутри одного VLAN, Hotspot и ограничение скорости автоматически не настраиваются. Опционально включается частичная изоляция клиентов одного гостевого SSID (`datapath.client-isolation`); другие точки и проводные гости не охватываются. Гостевой порт и радио
держатся отключёнными до применения VLAN Filtering; доступ к устройству всё равно может быть
утрачен, поэтому необходимы Safe Mode, резервная копия и консоль.

Для одного MikroTik доступны один статический маршрут к сети через LAN-шлюз и системные
сервисы: собственные DNS-серверы, DNS-кэш, локальная запись A, NTP и часовой пояс,
имя устройства и IP Cloud DDNS. DHCP и адресная таблица учитывают выбранный DNS. При двух
провайдерах можно включить проверку одного внешнего ICMP-узла для основного **статического**
WAN; в интерфейсе можно имитировать отказ узла. PPPoE/DHCP/LTE в роли основного WAN для
этой проверки, policy routing и данные функции в двухроутерной модели пока не поддерживаются.
Маршрут к контрольному IP закреплён за основным WAN: не используйте его как единственный DNS.
Модель не проверяет настоящие DNS/NTP/DDNS, удалённые сети или ICMP; ICMP-узел может не
ответить по собственной причине. DDNS использует сервис MikroTik и не обходит CGNAT.
Существующие соединения при переключении могут оборваться. Опционально доступно ограничение WinBox/SSH основной IPv4 LAN и отключение MAC-доступа и WebFig; необходимы проверка IP-доступа, консоль восстановления и отдельная оценка IPv6.

В лаборатории создаётся проект RouterOS 7: WireGuard, IKEv2 с заранее
импортированными сертификатами или L2TP/IPsec, а также публикации TCP/UDP на статические
адреса ПК/серверов. Параметры публикации доступны и при выборе прямой линии между ПК или
сервером и MikroTik. VPN-соединения и интернет-доступ не проверяются; для доступа снаружи
нужны белый IP и доступный сервис, при CGNAT/вышестоящем NAT нужна отдельная настройка.
Публикация увеличивает риски безопасности. Вход на резервном WAN может потребовать
отдельной маршрутизации ответов.

**Важно:** для двух MikroTik отображается только учебный план VRRP; готовая конфигурация
двух роутеров, синхронизация DHCP, NAT-соединений и VPN не генерируются. VRRP сам не
отслеживает доступность интернета за шлюзом. Трафик и переключения на схеме — учебные и не проверяют реальную сеть; отдельная CHR Windows не моделирует сценарий двух роутеров. VPN-ключи/пароли могут быть в командах; не
публикуйте их. Перед применением любых команд сделайте резервную копию, сверьте правила и
оборудование и протестируйте изменения. Для ручной настройки см. официальные руководства [WiFi](https://help.mikrotik.com/docs/spaces/ROS/pages/224559120/WiFi) и [Bridge VLAN Table](https://help.mikrotik.com/docs/spaces/ROS/pages/28606465/Bridge+VLAN+Table). Сторонние и старые снимки сохранены в репозитории для аудита, но скрыты из учебника; источники собственных снимков — `app/assets/img/own/SOURCES.md`. Покрытие оригинальными снимками пока неполное.

**Стенд моделирования** принимает: подсети LAN/гостевой сети и пулы адресов, тип и количество
провайдеров (PPPoE/DHCP/статика/LTE), основной и резервный канал, тип VPN, список внутренних
IP/портов для публикации наружу (и через какого провайдера), параметры Wi-Fi. На выходе —
проверка исходных данных (пересечения подсетей, конфликты портов, корректность failover),
таблица плана, учебный проект конфигурации RouterOS v7 и чек-лист приёмки. Команды необходимо проверить и адаптировать к устройству; проверка подключения провайдеров не гарантирует доступность интернета.

## Структура репозитория

```
app/                     # общее веб-ядро (общее для Android и Windows)
  index.html             # оболочка + форма стенда
  js/lab-sim.js          # учебная модель лаборатории
  js/lab.js              # карта и взаимодействие
  js/stand.js            # движок моделирования (без DOM, тестируется в Node)
  js/sec-*.js            # контент разделов учебника
  css/app.css            # стили
  assets/img/official/    # снимки документации MikroTik (источники — SOURCES.md)
  assets/img/examples/    # снимки независимого MikroTik Wiki (источники — SOURCES.md)
  assets/img/topology.svg # учебная схема сети (tools/gen-screens.js)
android/                 # проект Android (WebView-обёртка, подписанный APK)
windows/                 # проект Windows (Electron, установщик NSIS)
tools/                   # генератор схемы и модульные тесты
.github/workflows/       # сборка на GitHub Actions
```

Экспорт схемы PNG/GIF использует локально включённый gifenc 1.0.3
(MIT, `app/vendor/gifenc/LICENSE.md`, https://github.com/mattdesl/gifenc).
Код работает офлайн; GIF показывает только условный трафик модели.

## Сборка на GitHub Actions

Воркфлоу `.github/workflows/build.yml` запускается на **каждый push**:

1. **test** — `node --check` всего JS, регенерация и сверка SVG, модульные и DOM-тесты стенда и лаборатории;
2. **android** — Gradle 8.4 + JDK 17 → `assembleRelease` → **подписанный APK** → чистый `releases/MikroTik-Guide.apk` в ветке;
3. **windows** — `npm install` + `electron-builder --win` → установщик `MikroTik-Guide-Setup-x.y.z.exe` → артефакт `MikroTik-Guide-Windows`;
4. **release** — при создании тега `vX.Y.Z` создаётся черновик GitHub Release с обоими файлами; после проверки файлов и сборок его публикуют отдельно.

Скачать свежую сборку:

* **Чистый APK без упаковки** — файл [`releases/MikroTik-Guide.apk`](releases/MikroTik-Guide.apk)
  прямо в репозитории: CI перезаписывает его после каждой успешной сборки ветки (скачивается
  кнопкой Raw/Download файловой страницы GitHub — **без zip**);
* **Releases** — тег `vX.Y.Z` создаёт релиз с файлами `MikroTik-Guide-vX.Y.Z.apk` и
  `MikroTik-Guide-Setup-x.y.z.exe` (оба — чистые файлы, не архивы);
* **Actions → Artifacts** — Windows-установщик внутри ZIP. При сборке тега
  Actions также временно передаёт APK между заданиями как внутренний артефакт;
  пользователю следует брать чистый APK из релиза, а не из этого архива.

При запуске приложение проверяет **последний опубликованный стабильный GitHub Release**
и предлагает установить новую версию, только если в релизе есть файл для текущей
платформы. Кнопка **«⟳ Обновить»** позволяет проверить вручную. Сборки в ветке и
черновики релизов автоматически не обнаруживаются. Если текущая сборка новее релиза,
диалог сообщает об этом, а не называет её последней версией.
Установка не бесшумная: скачайте и откройте установщик и подтвердите установку в системе.
Для Android необходима та же подпись и более высокий versionCode; данные сохраняются при
совместимом обновлении поверх. Версия 1.11.0 ещё не содержит автопроверку, поэтому её
нужно один раз обновить вручную. Ключ подписи в этом публичном репозитории не является
секретом: любой, кто его скопирует, может подписать APK тем же ключом.

Сборку Android и Windows выполнять только на GitHub Actions. Локально допускаются
проверки кода и тесты, но не сборка приложения. Точные команды и порядок
публикации: [выпуск и обслуживание](docs/RELEASE.md).

## Подпись (постоянный ключ)

APK подписывается **постоянным ключом**, лежащим в репозитории:

* `android/keystore/release.p12` — PKCS12-кейстор (RSA-2048, самоподписанный сертификат, действует до 2061 г.);
* `android/keystore/keystore.properties` — алиас и пароли, используемые Gradle.

Одинаковая подпись и package id позволяют обновлять поверх совместимой предыдущей
версии при достаточно высоком versionCode и разрешении Android; фактическую установку
на устройстве необходимо проверять отдельно.

> ⚠️ **Внимание:** ключ и пароли намеренно размещены в открытом репозитории по требованию
> владельца. Любой, кто имеет доступ к репозиторию, может подписывать обновления этого
> приложения. Не используйте этот ключ для приложений с чувствительными данными; для
> публичных магазинов создайте отдельный ключ и храните его в секретах CI
> (`gradle.properties` / `keystore.properties` через GitHub Secrets).

## Требования

* Роутер MikroTik с RouterOS **v6.49+** или **v7.x** (примеры — под v7, отличия отмечены);
* WinBox 4.x (в разделах используется как основной инструмент, все команды дублируются для CLI);
* Android **8.0+** (minSdk 26); Windows 10/11 x64.

Пункты учебника допускают отдельную привязку проверенного оригинального снимка. Справочник MikroTik: https://manual.mikrotik.com/docs/introduction/

**Изолированная CHR:** кнопка «Пример CHR: изолированная» создаёт учебную схему с одним провайдером и ПК. Замена непустой схемы требует подтверждения. Кнопка не запускает CHR и не открывает сеть; в Windows пользователь отдельно запускает VM из карточки MikroTik и знакомится с лицензией. ПК и провайдер на схеме не становятся виртуальными машинами.

**Для продолжения разработки агентом:** начните с [AGENTS.md](AGENTS.md), очереди [docs/NEXT.md](docs/NEXT.md) и актуального состояния в [docs/HANDOFF.md](docs/HANDOFF.md); исторические заметки не заменяют проверку кода и релизов.
