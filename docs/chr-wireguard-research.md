# Исследование WireGuard для CHR

Режим находится в разработке: приложение по-прежнему блокирует VPN в CHR и не пробрасывает входящий UDP-порт. IKEv2 и L2TP/IPsec не проверены. Снимки интерфейса и peer в учебнике получены на отдельных одноразовых CHR и сами по себе не подтверждают соединение.

## Изолированный эксперимент

`.github/workflows/wireguard-chr-research.yml` запускает две настоящие CHR 7.23.8 на GitHub Linux runner. Их WAN соединены виртуальным UDP-сокетом только через loopback runner; один клиентский тестовый интерфейс LAN изолирован. Генератор приложения задаёт первой CHR интерфейс `wg-lab`, адрес `10.10.10.1/24`, одного peer с `10.10.10.2/32`, firewall и NAT. Вторая CHR получает другой одноразовый ключ и выступает клиентом. Для сети сервера `192.168.88.0/24` клиенту нужны как Allowed Address, так и маршрут через WireGuard. Ключи генерируются только для одноразовых VM, не печатаются и удаляются вместе с временными дисками.

- [41175498950](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41175498950): клиент достиг `10.10.10.1` по WireGuard, но `192.168.88.1` был недоступен: на клиенте отсутствовал маршрут к LAN. Workflow завершился ошибкой; маршрут добавлен в следующий тест.


ICMP до LAN-адреса самой серверной CHR — **не проверка forward до реального хоста в LAN**. Не проверены туннель из интернета, NAT/CGNAT, Windows и продакшен-оборудование. Применение генератора напрямую в этом исследовании не проверяет запуск через приложение, REST-сверку, диалоги или открытие VPN-портов пользователем. Блокировку можно рассматривать к снятию только после проверки этих сценариев и безопасного, явно согласованного способа подключения клиента.
