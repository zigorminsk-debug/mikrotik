код, GitHub Actions и начало `HANDOFF.md`; обновляйте этот файл после каждого этапа.

только в чате или во временном каталоге. Не храните пароли и личные данные.

## Новый запрос пользователя: сценарии по разделам учебника

В коде 1.19.11 для каждой страницы учебника есть карточка «Проверить на стенде». Первые реализованные сценарии — первичная настройка, IP, Interfaces, Bridge, Routing, System. Выбор проверяется до замены схемы; конфликты объясняются, неподдерживаемые функции заблокированы. Дополнительные разделы пока не реализованы — расширять только после проверки на настоящей CHR, не выдавая имитацию за готовность. Схема заменяется только с подтверждением, запуск CHR отдельный и только на Windows. Подробности и тесты: `docs/guide-lab.md`. [CI 41301094700](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41301094700) проверил пять сценариев в одноразовой CHR; 1.19.11 опубликован. Не забыть прежний главный запрос: автоснимки WinBox именно пользовательской схемы пока не готовы.

## Зафиксированные задачи

1. Продолжать учебник с первичной настройки и далее в порядке меню RouterOS,
   особенно LAN, VLAN и Wi-Fi. Каждый шаг требует оригинального подробного снимка
   WinBox соответствующего действия. `screenshot-audit.md` указывает пробелы в
   нумерованных списках; он не учитывает абзацы и динамические инструкции.
   `app/assets/img/own/SOURCES.md` описывает реальные источники изображений.
2. Продолжать Windows-лабораторию с настоящей CHR и выбранными настройками;
   Wi-Fi-радио, LTE, виртуальные клиенты, VPN пользователя и два физических
   роутера ещё не реализованы. Несовместимые настройки блокируются. Два WAN QEMU
   используют одно подключение компьютера, требуют отдельного согласия на каждый
   запуск и не моделируют две физические сети/две карты сервера.
3. Прямое физическое подключение по MAC и отправка схемы остаются отдельной
   незавершённой задачей. При обрыве возможен неизвестный частичный результат;
   сброс конфигурации требует отдельного явного подтверждения. См.
   `physical-router-plan.md`; не считать MNDP или виртуальную CHR физическим тестом.
4. После каждого этапа: документировать, тестировать на GitHub Actions, выпускать
   чистый APK и Windows EXE; сохранять релиз и тег 1.19.2 до нового согласия.
   Русские заметки о релизах хранить в `docs/releases/`. Все сборки только в CI.

CI [41299657462](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41299657462) дополнительно открыл карточку LAN-адреса в фоновом WinBox без изменения настройки и снял видимые поля; снимок проверен визуально. Выбор строки фиксирован координатой, это не надёжная автоматическая съёмка пользовательской схемы. Следующий ключевой шаг — выбор нужной записи по данным и проверка, а не подбор координат.

## Главный приоритет: снимки настроек конкретной схемы

Пользователь уточнил: после составления схемы и успешной проверки нужно получать для просмотра и обучения **оригинальные снимки WinBox со всеми настройками именно этой схемы**, а не заранее снятые общие изображения. Пользователь выбрал сначала Windows; перенос/самостоятельное создание на Android пока не согласованы. Текущая кнопка проверяет только учебную модель и снимков не создаёт. Нельзя заменять настоящие снимки рисунками, старыми кадрами или выдавать частичную съёмку за полную. Не запускать физический маршрутизатор; виртуальный CHR, её лицензия и отдельное подтверждение сетевого режима остаются обязательными. [Первая попытка Windows CI 41290948302](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41290948302) настроила и проверила одноразовую CHR, но съёмка WinBox не завершилась; снимок не получен. Повтор [41291175396](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41291175396) не увидел элемент IP через UI Automation; аутентификация не подтверждена. Повтор [41291700812](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41291700812) подтвердил аутентификацию WinBox и снял настоящее рабочее окно CHR с конфигурацией примера, но координаты открыли Mesh, а не IP → Addresses. [CI 41292125262](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41292125262) визуально подтвердил расположение меню IP на этом runner. Это не снимок настройки и не результат для пользователя; [CI 41292391504](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41292391504) открыл IP → Addresses виртуальной CHR с сетями примера, но столбец адресов обрезан. Требуется получить читаемый снимок и отдельно сверить конкретные значения; пользовательский поток не реализован. Сначала CI-прототип: план из реальной схемы приложения → одноразовая CHR на Windows → проверка полученных настроек → оригинальный WinBox → снимок конкретной настройки, без пользовательских секретов; затем безопасная интеграция с UI, перечень неподдержанных действий, хранение и приватность снимков. Нельзя передавать реальные пароли в аргументах процесса или показывать их на снимках.

[CI 41292662280](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41292662280) получил читаемый оригинальный WinBox IP → Addresses с адресами фиксированного UI-примера; снимок и точные ограничения сохранены в `docs/lab-winbox-screenshots.md` и `docs/research/winbox-scheme-addresses-ci.jpg`. Это одно окно, только CI, не готовая пользовательская функция. [CI 41298059529](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41298059529) проверил адресный ввод одноразового пароля и фоновую навигацию адресными сообщениями в двух окнах WinBox при другом окне в фокусе; PrintWindow снимки визуально проверены. Снимок проверен и сохранён; это ещё не доказательство безопасности или надёжности. Следующий шаг — устранить координатную навигацию, проверить безопасность, список всех поддерживаемых окон и связать снимки с конкретной схемой; не копировать CI-механизм в продукт без проверок.
