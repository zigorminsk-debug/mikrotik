# Архитектура и проверка изменений

Обзор архитектуры; некоторые исторические примеры относятся к версии 1.18.0 и могут не отражать более поздние изменения. Текущее состояние задач и пользовательские договорённости — в [HANDOFF.md](HANDOFF.md), выпуск — в [RELEASE.md](RELEASE.md).

## Состав

- `app/` — общее офлайн веб-приложение, встроенное в Android и Windows. `index.html`, `css/app.css`, `js/app.js` реализуют оболочку, навигацию и проверку релизов. `js/version.js` должен совпадать с версией Android и Windows.
- `app/js/guide-core.js`, `sec-*.js`, `sec-z-router-menu.js` — учебник. Порядок навигации строится последним файлом; старые разделы оставлены для переиспользования, но скрыты из навигации. Источники собственных снимков — `app/assets/img/own/SOURCES.md`; старые и сторонние файлы в `official/` и `examples/` не следует показывать как собственные WinBox 4.
- `app/js/lab.js` и `lab-sim.js` — состояние схемы, валидация, модель и генерация команд. `lab-sim.js` доступен в Node без DOM. `lab-export.js` и vendored `gifenc` сохраняют PNG/GIF учебной схемы, не редактируемый проект и не реальный трафик.
- `app/js/stand.js` — отдельный конструктор проекта и команд; его возможности нельзя автоматически приравнивать к выполненным настройкам CHR.
- `android/` — WebView-оболочка. `MainActivity.java` загружает локальные assets и выполняет проверку GitHub Release через JavaScript-мост. Сетевые ссылки открываются внешним приложением. `android/app/build.gradle` задаёт package id, versionCode и подпись.
- `windows/main.js`, `preload.js` — Electron main и узкий мост для главного renderer. Пользователь передаёт состояние схемы, но не произвольные команды или пути к программе. `windows/scripts/copy-app.js` переносит общее ядро в игнорируемый `windows/www/` при сборке на CI.
- `windows/chr/plan.js` заново проверяет схему в main-процессе, отбрасывает неподдерживаемые группы и формирует ожидаемые значения; `console.js` настраивает одноразовую CHR по serial; `session.js` управляет QEMU и очисткой; `verify.js` считывает состояние CHR по REST; `download.js` безопасно загружает и проверяет официальный образ; `online.js` ограничивает проверенный сетевой сценарий; `network-warning.js` содержит обязательное предупреждение.
- `tools/windows/chr-supervisor.c` использует Windows Job Object для контроля QEMU и остановки дочернего процесса. `windows/scripts/prepare-qemu.ps1` на GitHub скачивает зафиксированный QEMU, исходники и лицензии с проверкой хешей и кладёт их в установщик.
- `tools/test-*.js` и `.github/workflows/` разделяют unit/DOM-тесты, интеграцию с настоящей CHR, проверку Electron и сборку релиза. Сборочные артефакты, зависимости, временные VM и загруженные исходники не добавляются в Git, кроме специально сохраняемого `releases/MikroTik-Guide.apk`.

## Безопасность процесса CHR

1. В renderer пользователь сохраняет конфигурацию и нажимает кнопку. Main принимает запрос только из главного окна, проверяет размер и заново строит план. Не принимать готовый RouterOS-скрипт из renderer.
2. Один статический WAN работает изолированно. NTP применяет и сверяет только клиент, адрес сервера и часовой пояс; с изолированным интернетом синхронизация не проверяется. В сетевом двух-WAN режиме NTP разрешён только вместе с существующим отдельным согласием на сеть; само приложение не утверждает, что синхронизация выполнена. В ограниченном варианте двух WAN до загрузки/запуска выводится нативное предупреждение и согласие **для каждого запуска**. `online.js` проверяет конкретные адреса и порты; ни адреса, ни другой выбор пользователя не заменяются автоматически. Два сегмента используют один Windows-хост и могут обращаться к нему и LAN.
3. `download.js` использует закреплённый HTTPS-адрес и хеши ZIP/образа, проверяет архив и сохраняет неизменяемый кэш. Письмо происходит в отдельную временную копию образа. Не отключать проверки хешей и не скачивать бинарник с произвольного URL из renderer.
4. Management CHR вынесен на отдельный ether6; host forward привязан к `127.0.0.1`, входящий WAN host forward не создаётся. Случайный пароль не выводится в лог. Встроенное окно WebFig ограничено ожидаемым локальным адресом; внешние запросы, новые окна и permissions запрещены.
5. План применяется последовательно, результат проверяется на версии/архитектуре и выбранных настройках через REST. Ошибка или несовпадение останавливают сессию, не выдавая частичный успех. `stop()` безопасен при повторных и одновременных вызовах; временный диск удаляется при закрытии окна.

CI-only флаги в `session.js` используются отдельными тестами. Нельзя включать произвольный небезопасный режим через renderer или выдавать его за изолированный. Для прав доступа к услугам Windows и LAN см. [chr-internet-plan.md](chr-internet-plan.md).

## Проверки и их границы

| Что проверить | Где | Что не доказывает |
|---|---|---|
| Схема, команды и валидация | `tools/test-lab.js`, `tools/test-stand.js` | Реальное выполнение RouterOS/трафик |
| DOM, версии, сетевой выбор | `tools/test-dom.js`, `test-lab-dom.js`, `test-chr-dual-wan-dom.js` | Настоящий WebView, Windows диалоги или VM |
| Plan, serial, REST, IPC, cleanup | `tools/test-chr-{plan,console,verify,session-unit,online,main}.js` | Физическую сеть или полный запуск установленного EXE |
| Реальная одноразовая CHR | `windows-chr-nat.yml`, `windows-chr-dual-integration.yml` | Независимые ISP, клиентскую VM, проверку TLS-доверия; в интеграции диалоги и загрузка образа подменены |
| PNG/GIF | `windows-export.yml`, `test-export-electron.js` | Ручной нативный файловый диалог или реальный трафик |
| Установщик | `build.yml`, `smoke-packaged.ps1` | Полный сквозной сценарий запуска CHR из пользовательского окна |
| Снимки | `routeros-capture.yml`, `windows-chr-warning-capture.yml`, `audit-screens.js` | Покрытие действий вне статических нумерованных списков; нужна визуальная проверка |

Изменяя новые роли, добавляйте отрицательные тесты: отсутствие обязательных параметров, запрещённые комбинации, ошибочный ответ CHR, лишние адреса/маршруты и очистку после ошибки. Сначала проверьте изолированную конфигурацию на одноразовом GitHub runner, затем явно документируйте доступность и ограничения.

## Обновления приложения

`app.js` сравнивает текущую версию с `https://api.github.com/repos/zigorminsk-debug/mikrotik/releases/latest`, принимает только стабильный опубликованный релиз и проверяет, что ссылка файла относится к соответствующему тегу этого репозитория. Черновики и APK в ветке в этот механизм не входят. Android использует нативный фоновый HTTP-мост из-за ограничений `file://`; выбранная ссылка на APK открывается через внешнее приложение. Пользователь сам скачивает файл и подтверждает установку Android. Обновление поверх возможно только при совпадающем package id/сертификате и более высоком versionCode. Проверка сертификата Android — обязанность системы установки; публичный ключ проекта не обеспечивает защиту от подделки третьей стороной.
