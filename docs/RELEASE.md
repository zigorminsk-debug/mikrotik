# Сборка, подпись и выпуск

Все сборки APK и Windows-установщика выполняются **на GitHub Actions**. Не запускайте локально `gradle assembleRelease` или `electron-builder`: они не заменяют согласованный CI. Запуск отдельных тестов локально допустим, но проверка реальной CHR и сборка установщика проводятся на Windows runner.

## Контракт версий и подпись

При выпуске обновить одновременно:

1. `app/js/version.js` — `APP_VERSION`;
2. `android/app/build.gradle` — `versionName` и строго более высокий `versionCode`;
3. `windows/package.json` и `windows/package-lock.json` — ту же версию;
4. учебник, README и документацию об изменениях и ограничениях.

Текущая кодовая версия — 1.16.0, Android code 23. При установке поверх требуется совпадающий package id `by.mikrotik.tutor`, подписывающий сертификат и более высокий versionCode. Ключ PKCS12 намеренно находится в `android/keystore/` по требованию владельца. Это **публичный ключ**, не средство доверия к автору: любой, у кого он есть, может подписать приложение той же подписью. Не выводите пароли или содержимое ключа в логи и не используйте его для других приложений. Любая смена ключа препятствует обычному обновлению поверх старой версии. Сверьте отпечаток сертификата в CI через `apksigner verify --print-certs`; ранее проверенный SHA-256 сертификата: `71a7bab089b395259e0c9980130652c5f996319892a928b1e4a5025ab602d31a`.

## Веточная сборка

- `Build` в `.github/workflows/build.yml` запускается на push и сначала выполняет тесты. Android job собирает подписанный APK и коммитит **один чистый** `releases/MikroTik-Guide.apk` в ту же ветку. Внутри Git-истории могут остаться старые бинарные объекты: их переписывание — отдельное разрушительное действие.
- Windows job собирает EXE и проверяет установку/запуск через `windows/scripts/smoke-packaged.ps1`. QEMU, исходники и лицензии зафиксированы хешами в `prepare-qemu.ps1`; сам образ CHR в EXE не включён и запрашивается при первом запуске после ознакомления с лицензией.
- При нескольких CI-запусках APK-бот может добавить коммит после ваших изменений. Перед push делайте `git fetch origin`, проверяйте `git status` и переносите свои коммиты поверх актуальной удалённой ветки. Не используйте `git reset --hard`. В Arena используйте только назначенную сессии ветку.
- Команды `node tools/test-stand.js`, `node tools/test-lab.js`, `node tools/test-chr-plan.js`, `node tools/test-chr-verify.js`, `node tools/test-chr-session-unit.js`, `node tools/test-chr-online.js` и `node tools/test-chr-main.js` проверяют логику. Для DOM-тестов требуются зависимости `npm ci --prefix tools`; затем `node tools/test-dom.js`, `node tools/test-lab-dom.js`, `node tools/test-chr-dual-wan-dom.js`. Это тесты, не сборки приложения.
- Для реального RouterOS и изменённых настроек нужны отдельные GitHub Actions: `Windows CHR NAT verification`, `Windows CHR dual WAN integration` и соответствующие тесты. Они не заменяют ручное или автоматизированное сквозное тестирование установленного EXE.

## Выпуск стабильной версии

1. Убедиться, что тесты, сборка обеих платформ и соответствующие реальные CHR/Electron проверки прошли для нужного коммита. Оценить ограничения и риски; не публиковать непроверенную возможность как готовую. `Build` в ветке не делает новую версию последней для обновления пользователей.
2. Проверить, что тег версии отсутствует, все четыре версии совпадают, а Android code повышен. Опубликовать тег `vX.Y.Z` на **проверенный** коммит через разрешённый в среде механизм. Для GitHub API используются `ref=refs/tags/vX.Y.Z` и полный SHA коммита; не перемещайте существующий тег и не используйте `[skip ci]`.
3. Push тега запускает `Build`: `release` создаёт **черновик** с чистым `MikroTik-Guide-vX.Y.Z.apk` и `MikroTik-Guide-Setup-X.Y.Z.exe`. Дождаться успеха теговой сборки. Через `gh release view vX.Y.Z --json isDraft,isPrerelease,assets,url` проверить имена, непустые размеры и `state=uploaded`; проверить успешную подпись APK в журнале CI.
4. Подготовить понятные русские release notes: что добавлено, что действительно проверено, ограничения, предупреждение о публичном APK-ключе, условия установки и размер EXE. Не заявлять проверку клиентской VM, независимых провайдеров, TLS или системного диалога, если её не проводили.
5. Опубликовать проверенный черновик с отметкой latest: `gh release edit vX.Y.Z --draft=false --latest --notes-file <файл>`. Проверить `gh api repos/zigorminsk-debug/mikrotik/releases/latest`, имена и прямые ссылки файлов. Обновлятор приложения проверяет именно этот опубликованный stable `latest`, а не APK в ветке и не черновик.
6. В теговом `Android published update discovery` предыдущий APK устанавливается в Android-эмулятор и проверяет, что опубликованный latest предлагает новую версию и APK. Дождаться результата, прежде чем удалять предыдущий релиз; тест также устанавливает новый APK поверх предыдущего через adb, но не проверяет загрузку через браузер и диалоги системного установщика.
7. Если приложение Android находит обновление, оно открывает ссылку на APK; пользователь скачивает файл в браузере и подтверждает установку средствами Android. Автоматическая бесшумная установка не реализована. Не удалять предыдущий работающий релиз до проверки нового и подтверждения выбранной политики хранения.

Теговые артефакты Actions могут передаваться между заданиями как внутренний ZIP; для пользователя всегда публикуется чистый APK. Путь `releases/MikroTik-Guide.apk` относится к выбранной ветке и не обязательно совпадает с последним опубликованным релизом.

## Удаление старых релизов

По решению владельца поддерживается только актуальный опубликованный релиз; удаление старых GitHub Releases **и связанных тегов** отключает прежние прямые ссылки на APK/EXE и не удаляет коммиты/объекты из Git-истории. Не удаляйте актуальный релиз до публикации и проверки замены. Перед каждой последующей уборкой проверьте, сохраняется ли это разрешение, и явно перечислите, какие версии будут удалены. При авторизации на удаление страницы и тега используется `gh release delete <точный-тег> --yes --cleanup-tag`; после операции проверить `gh release list` и список тегов. Не переписывать историю Git без отдельного разрешения.

Последняя проверка: [CI 41111931034](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41111931034) нашёл опубликованную 1.16 в эмуляторе с установленной 1.15 и затем обновил APK поверх через adb. Интерактивные браузер и системный установщик не проверялись. После проверки релиз и тег 1.15 удалены, потому повторить этот переход из Releases теперь нельзя; перед следующим выпуском сохранить 1.16 до проверки замены. Тест при запуске из ветки требует наличия **другого** опубликованного релиза, а при запуске по тегу сохраняет предыдущий APK до публикации нового.

## Если что-то не работает

- «Не найдена новая версия»: сравнить версию на устройстве с `gh api repos/zigorminsk-debug/mikrotik/releases/latest --jq .tag_name`. Если новая сборка есть лишь в ветке или черновике, updater её не увидит. Проверить наличие корректного APK asset, сетевой доступ и отсутствие API rate limiting. Ветка с версией выше latest отображается как более новая сборка, а не как обновление.
- APK не устанавливается поверх: проверить package id, фактический versionCode, отпечаток подписи и разрешение Android на установку из выбранного источника. Не предлагать удаление приложения без предупреждения о возможной потере данных.
- Прямая загрузка release-assets может быть недоступна из отдельных sandbox-сред; проверять asset и подпись на GitHub runner, не считать локальный EOF доказательством повреждения.
- `gh`/`git` могут временно возвращать 5xx или конфликт APK-бота. Сначала проверить, что уже отправлено и что CI создал, затем безопасно fetch/rebase; не повторять операции вслепую.
