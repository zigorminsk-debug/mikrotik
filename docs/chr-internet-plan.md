# Интернет и выбранные настройки в виртуальной лаборатории

Пользователь разрешил использование интернет-соединения компьютера. Это не
означает, что функция уже доступна в интерфейсе или что виртуальная сеть
безопасно изолирована. Текущая версия приложения не подключает WAN CHR к
интернету; опыт с подключением выполняется только на одноразовом Windows
runner GitHub Actions (`tools/test-chr-internet.js`).

## Опыт

Для пробной CHR используется QEMU user-mode NAT на одном WAN с тестовыми
10.0.2.20/24 и 10.0.2.2. Порт управления остаётся отдельным и доступен только
через loopback; WAN-пробросов с хоста в CHR не добавлено. Выполняется запрос
из самой CHR; тест проверяет соединение, но намеренно не проверяет доверие TLS.
Это не подтверждает работоспособность NTP, IP Cloud, ICMP и схемы с реальными
настройками провайдеров. В тесте [41079535389](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41079535389) соединение с github.com достигло HTTP-ответа, но RouterOS fetch завершился ошибкой `ERROR parsing http: too big field size`; поэтому неудачный запрос на этот адрес сам по себе не доказывает отсутствие сети. Отдельно проверяется более короткий публичный ответ. Не подменять выбранные пользователем адреса тестовыми.

Пользователь разрешил предлагать такой режим **после отдельного явного подтверждения при каждом запуске**, зная о возможном доступе к компьютеру и устройствам локальной сети. Это не означает, что можно включать его без проверки, открывать входящие WAN-порты или представлять два виртуальных WAN на одной сети как независимых провайдеров.

Важно: QEMU user-mode NAT с `restrict=off` способен открывать соединения с
сервисами хоста через виртуальный шлюз и может обращаться к локальной сети.
Он не является песочницей, ограничивающей трафик только интернетом. До
предложения функции пользователю нужны отдельное предупреждение, управление
разрешением при запуске, безопасная политика для хоста и сети, проверка с
помощью тестов, а также отсутствие внешнего проброса в гостевую систему.

## Остальные требования

- Сохранить и подтвердить выбранные параметры через опрос настоящей CHR;
  попытка применить неподдерживаемую настройку должна останавливать запуск.
- DHCP-провайдер требует DHCP-службы в виртуальном сегменте; PPPoE —
  действующего виртуального PPPoE-сервера с нужными учётными данными. Одного
  SLIRP NAT для PPPoE недостаточно.
- Для проверки резервирования нужны два управляемых сетевых сегмента; для двух
  MikroTik — две CHR, отдельные виртуальные связи и проверка реального перехода.
  Два NAT-подключения через один компьютер не являются независимыми интернетами
  и не воспроизводят ситуацию двух физических сетевых карт сервера.
- Для Wi-Fi и LTE нужны поддерживаемое реальное радио или модем: CHR не
  эмулирует их. Не заменять это имитацией и не обещать неподтверждённое.
- Установленный Electron → согласие → запуск → настройки → WebFig → очистка
  пока не проходил автоматизированный сквозной тест. Скриншоты всех действий
  также ещё не собраны.

## Опыт с двумя виртуальными WAN

CI-only опыт добавляет к проверенной CHR второй QEMU user-mode NAT на ether4
(10.0.3.0/24), выключает ether1, проверяет активный резервный маршрут и
запрос из CHR, затем включает ether1 и проверяет возврат. Это **не** две
физические линии: оба сегмента используют одну сеть Windows-runner. Для
эксперимента отключается ping-проверка шлюза, поскольку QEMU user-mode NAT
может не отвечать на ICMP. Проверка недоступности интернета за работающим
шлюзом, TLS-доверия, пользовательских адресов и трафика клиентов не покрыта.
В приложении экспериментальные NAT-сегменты не включаются; безопасность хоста
и физической сети и согласие на этот уровень доступа должны быть решены до
включения. Сам по себе успешный тест не даёт основания снимать блокировку
резервирования в приложении.

Результат: [Windows CI 41080998213](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41080998213) прошёл. Из CHR получен короткий HTTPS-ответ сначала по основному, затем после выключения ether1 по резервному маршруту, затем после включения ether1 снова по основному. В тесте не проверялась доверенная TLS-цепочка, доступ клиентской ВМ, обрыв внешней сети при поднятом интерфейсе или реально независимые интернет-провайдеры.

## Подготовка проверки выбранных двух WAN

В CI готовится отдельный запуск с двумя статическими WAN, где **оба** адреса,
членство в WAN и маршруты применяются из выбранной конфигурации и сверяются
через REST, а не добавляются вручную после запуска. Оффлайн-проба использует
документационные 198.51.100.2/30 и 198.51.101.2/30; интернет-испытание
использует ровно 10.0.2.20/24 с шлюзом 10.0.2.2 и 10.0.3.20/24 с шлюзом
10.0.3.2, DNS 10.0.2.3 и 10.0.3.3. Адреса являются адресами виртуальных NAT,
не данными пользователя или настоящих провайдеров. Запрос проверяет короткий
ответ без проверки доверия TLS. Эксперимент наблюдает изменение маршрута
после отключения интерфейса и восстановление, не сбой интернета за работающим
интерфейсом. Клиентских VM и входящего WAN-проброса в опыте нет.

`windows/chr/online.js` ограничивает эксперимент этими проверяемыми
параметрами. Функция не подменяет введённые адреса. Производственный
`chr:launch` пока не передаёт разрешение на сетевой режим и продолжает
блокировать два WAN: сначала нужны результаты испытания, предупреждение в
нативном диалоге и проверка всего пути запуска в Windows.
