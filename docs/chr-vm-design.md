# Виртуальная RouterOS в лаборатории: текущий статус

**В разработке.** Ни запуска CHR из приложения, ни кнопки открытия RouterOS, ни применения
настроек пока нет. `LabEngine.chrPreflight` только оценивает некоторые
известные ограничения и всегда возвращает `available: false`. Пустой список
`blockers` не означает, что схема поддерживается или проверена на RouterOS.
Предварительная проверка не возвращает пароли, команды или имена устройств.
Проверка работает с текущей моделью и не заменяет проверку виртуальной машины.

На GitHub Actions в Windows подтверждена загрузка CHR 7.23.8 в QEMU и
выполнение тестового проекта с LAN, VLAN, DHCP, NAT и firewall; значения
нескольких настроек прочитаны обратно из RouterOS. Отдельная проверка
использует разрабатываемый модуль консоли Node.js. Это эксперимент на
одноразовом runner, а не запущенная пользователем виртуальная машина и не
проверка всех сценариев. [Запуск теста](https://github.com/zigorminsk-debug/mikrotik/actions/runs/41043934855).

## Принятые требования

- Windows: QEMU входит в установщик; официальный образ CHR загружается при
  первом запуске непосредственно у MikroTik, после ознакомления с условиями
  лицензии и согласия пользователя. Android — отдельный этап.
- ВМ, а не физический роутер; все виртуальные порты по умолчанию изолированы
  от физических интерфейсов, без bridge/TAP и автоматического доступа в интернет.
  Вход управления привязывается только к loopback. Не открывать управляющий
  порт наружу и не передавать данные неизвестным сервисам.
- Одна ВМ не заменяет модель двух маршрутизаторов или виртуальные ПК и
  провайдеры; Wi-Fi-радио и LTE-модем не эмулируются. Не скрывать выбранные,
  но неподдерживаемые настройки. До подтверждения совместимости не применять
  частичную конфигурацию, не подменять команды похожими и не объявлять успех.
- Зарезервирована **для предварительной проверки**, пока без реализации,
  отдельная подсеть управления `172.31.254.0/24`; пересечение с настройками
  схемы блокируется. Реальная реализация должна проверить конфликты и назначение
  адреса управления, недоступного из внешней сети и пользовательских портов.
- При первом запуске CHR нужно безопасно обработать начальную настройку пароля;
  не сохранять секреты в логах, параметрах командной строки или надолго на
  диске. Отдельная временная копия диска и вся временная конфигурация должны
  удаляться при остановке; предусмотреть восстановление после сбоя приложения.
- Команды должны проверяться по результату выполнения в CHR, а не только по
  появлению окна. В случае ошибки явно указать неподтверждённые настройки и
  остановить применение; VM с частично применённой конфигурацией не выдавать за
  готовую. Интерфейс должен позволять явно остановить гостевую систему.

## Что необходимо до выпуска

1. Выбрать и закрепить сборку QEMU для Windows, проверить хэш и состав архива,
   совместимость, исходный код и лицензии всех компонентов. Кандидат:
   [portable QEMU 11.1.2](https://github.com/jzombie/lab-qemu-portable/releases/tag/qemu-v11.1.2),
   Windows x64 архив с SHA-256
   `67f298f79b7b110f633a6656eb742d5a919cdf5a55d92ed184ac0195c77a7a5c`
   согласно метаданным релиза GitHub. Это не проверка содержимого или лицензий;
   пригодность кандидата не установлена. Нельзя включать его в сборку до этого.
   В [скрипте упаковки кандидата](https://github.com/jzombie/lab-qemu-portable/blob/main/scripts/package-qemu-windows.sh)
   копируются исполняемые файлы, firmware и DLL, но нет явного копирования
   каталогов лицензий DLL. Нужно установить состав и версии зависимостей,
   собрать соответствующие лицензии и исходные тексты (либо собрать QEMU и
   зависимости самостоятельно с фиксацией версий); одной ссылки на QEMU
   недостаточно для проверки условий всех включённых компонентов.
2. Довести до интеграции загрузку и проверку образа (подготовленный модуль
   пока не подключён к приложению), управление жизненным циклом QEMU,
   изоляцию и узкий preload/IPC без произвольных команд и путей из интерфейса.
3. Разработать и проверить импорт и подтверждение команд именно для CHR. Для
   выбранных, но не реализованных функций блокировать запуск с объяснением;
   для IKEv2 отдельно проверить сертификаты, для L2TP/IPsec и WireGuard — реальные
   параметры и результат. Наличие команды в генераторе модели не доказывает её
   применимость или корректность на CHR.
4. Провести интеграционный тест на настоящей CHR на GitHub Actions и Windows:
   проверять результат каждой настройки, ошибки, таймауты, изоляцию, очистку,
   перезапуск, поведение при прерывании и секреты. Сборка и тесты Windows — CI.
5. Только после этого добавить действующую кнопку в настройки MikroTik, статусы
   и инструкции со снимками реальных действий. Free-лицензия CHR имеет
   ограничения скорости; см. [условия MikroTik](https://mikrotik.com/software/legal)
   и [описание CHR](https://help.mikrotik.com/docs/spaces/ROS/pages/18350234/Cloud+Hosted+Router+CHR).
